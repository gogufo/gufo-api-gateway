## MCP Gateway

Gufo supports forwarding Model Context Protocol (MCP) requests to a configured microservice.

Gufo does not implement MCP tools or MCP business logic. It acts as a transport adapter between an MCP client and the target microservice.

### Architecture

```text
MCP Client / Hermes
        |
        | HTTP POST
        v
Gufo API Gateway
        |
        | gRPC / pb.Request
        v
Configured MCP Microservice
        |
        | MCP JSON-RPC
        v
Gufo
        |
        | HTTP response
        v
MCP Client / Hermes
````

The MCP protocol implementation belongs to the target microservice. Gufo is responsible only for transporting the MCP request and response between HTTP and the existing gRPC infrastructure.

### Configuration

MCP is configured using two environment variables:

```yaml
- name: GUFO_MCP_PATH
  value: "/api/v1/mcp"

- name: GUFO_MCP_MODULE
  value: "test"
```

Both variables must be present for the MCP endpoint to be registered.

There is no separate `GUFO_MCP_ENABLED` setting.

For example:

```text
GUFO_MCP_PATH=/api/v1/mcp
GUFO_MCP_MODULE=test
```

When configured, Gufo registers:

```text
POST /api/v1/mcp
```

and forwards requests to the `test` microservice.

### Request flow

An MCP JSON-RPC request is received by the Gufo MCP endpoint:

```text
POST /api/v1/mcp
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list"
}
```

Gufo preserves the original JSON payload and places it into the existing `pb.Request`:

```go
&pb.Request{
    Module: "test",
    Path:   "/api/v1/mcp",
    Method: pb.Method_METHOD_POST,
    Body:   /* raw MCP JSON */,
    Context: &pb.RequestContext{
        Meta: map[string]string{
            "mcp": "true",
        },
    },
}
```

The `mcp` metadata flag identifies the request as an MCP request to the target microservice.

No changes to the existing protobuf definition are required.

### Authentication

Gufo preserves the existing authentication mechanism and forwards authentication information from HTTP headers using the same authentication mapping used by normal API requests.

Supported authentication configuration remains controlled by the existing Gufo security settings.

### Response flow

The MCP microservice returns the MCP JSON-RPC response through the existing `pb.Response`:

```text
Response.Data["mcp"]
```

The value contains the raw MCP JSON payload.

Gufo extracts this payload and returns it directly to the MCP client:

```text
HTTP 200
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    ...
  }
}
```

Gufo does **not** wrap MCP responses in the normal Gufo REST response envelope.

### Error handling

Transport or gateway errors generated by Gufo are returned as JSON-RPC errors.

For example:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32603,
    "message": "MCP transport error"
  }
}
```

Errors generated by the MCP microservice are returned unchanged as part of the MCP JSON-RPC response.

### Separation from the REST API

The MCP endpoint is registered separately from the normal REST API:

```text
/api/v1/mcp
    |
    +--> handler.MCP
          |
          +--> gRPC transport
                |
                +--> MCP microservice

/api/v1/*
    |
    +--> handler.API
          |
          +--> existing REST processing
```

The existing REST request processing path is not modified by MCP support.

### MCP implementation boundary

Gufo intentionally does not contain:

* MCP tool definitions
* `tools/list` implementation
* `tools/call` implementation
* trading/business logic
* MCP tool authorization logic
* MCP response generation

These responsibilities belong to the configured MCP microservice.

For the current trading platform, the target is:

```text
GUFO_MCP_MODULE=test
```

Therefore `test` is the MCP server, while Gufo remains the gateway.

### Current transport scope

The current Gufo implementation accepts MCP JSON-RPC requests using HTTP POST and forwards the request/response transparently.

More advanced MCP transport features, including streaming/SSE behavior or protocol-version-specific transport handling, should be implemented only if required by the MCP client/server compatibility target.

The current architecture intentionally keeps those concerns out of the Gufo gateway.
